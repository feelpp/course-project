= Apptainer for reproducible scientific work

== Why this matters

A colleague should be able to run your computation without reconstructing your laptop. Apptainer packages a Linux application environment in an image and runs it under your user identity on a compatible Linux host. It fits shared scientific/HPC systems where users do not administer the machine.

== Learning objectives

Distinguish an image from an execution; pull and inspect a SIF; run commands; expose inputs and outputs deliberately; record enough information to repeat a run.

== Mental model

----
image (software environment) + host inputs + command/configuration
                           ↓
                  running process as you
                           ↓
                     host output files
----

An image is a file; a container execution is a process using that environment. A normal SIF image is read-only. Your home/current directory and other host paths may be mounted automatically according to site configuration. An explicit bind mount gives a stable path for an input or output directory. `--cleanenv` limits inherited environment variables; it does not hide host files or make an execution fully isolated.

== Docker and Apptainer

[cols="1,2,2",options="header"]
|===
|Aspect |Docker |Apptainer
|Typical workflow |Build OCI images and operate services through a container engine. Rootless Docker also exists.
|Run scientific jobs under the invoking user's identity, often from a single SIF file, alongside a scheduler.
|Image exchange |OCI registries store layers and image manifests.
|`docker://` can pull an OCI image and convert it to SIF; a Docker daemon is not needed for this operation.
|HPC fit |Availability depends on cluster policy and runtime integration.
|Designed for shared scientific systems; filesystem, MPI and GPU compatibility still need attention.
|===

A container shares the host kernel. It is not a virtual machine or a guarantee of identical numerical results on different hardware.
