= Lab 4 · Run and deliver a C++ program with Docker
:page-pagination:

Package the executable from xref:software:repo/cmake-presets-lab.adoc[Lab 3] and run the same sample on the host and in a container. By the end, a person with Docker and the sample input can reproduce the result.

== 1. Install the Release executable

Add this line after the executable target is declared in `CMakeLists.txt`:

[source,cmake]
----
install(TARGETS vector-norm RUNTIME DESTINATION bin)
----

Run from the project root:

[source,bash]
----
cmake --preset release
cmake --build --preset release
ctest --preset release
cmake --install build/release --prefix "$PWD/build/stage"
mkdir -p out
./build/stage/bin/vector-norm samples/vector.txt out/norm.txt
----

The install rule gives the executable a predictable location that the Docker build can copy.

== 2. Build an image

Check `docker version`. If the Docker engine is unavailable, follow the xref:docker/docker-install.adoc[installation guide]. Add a `.dockerignore` at the root:

[source,text]
----
.git
.github
build
out
CMakeUserPresets.json
----

The build context is the directory passed to `docker build`. Docker reads the source files from that directory. Excluding `build/` ensures compilation starts with the source and avoids copying binaries compiled on the host.

Create a `Dockerfile` at the root of the practice repository:

[source,dockerfile]
----
FROM ubuntu:24.04 AS build
RUN apt-get update \
    && apt-get install -y --no-install-recommends g++ cmake ninja-build libeigen3-dev \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /src
COPY . .
RUN cmake --preset release \
    && cmake --build --preset release \
    && ctest --preset release \
    && cmake --install build/release --prefix /stage

FROM ubuntu:24.04
RUN apt-get update \
    && apt-get install -y --no-install-recommends libstdc++6 \
    && rm -rf /var/lib/apt/lists/*
COPY --from=build /stage/bin/vector-norm /usr/local/bin/vector-norm
ENTRYPOINT ["/usr/local/bin/vector-norm"]
----

The first stage compiles and runs tests. The final stage contains the installed program and its runtime environment. The entry point receives the arguments passed after the image name. See the xref:docker/dockerfile-basics.adoc[Dockerfile reference] for the build context and instruction syntax.

== 3. Run the image with local input and output

[source,bash]
----
docker build -t vector-norm:lab .
mkdir -p container-out
docker run --rm --user "$(id -u):$(id -g)" \
  --mount "type=bind,source=$PWD/samples,target=/input,readonly" \
  --mount "type=bind,source=$PWD/container-out,target=/output" \
  vector-norm:lab /input/vector.txt /output/norm.txt
test "$(cat container-out/norm.txt)" = 5
cmp out/norm.txt container-out/norm.txt
----

The container sees the input at `/input/vector.txt` and writes into the host's `container-out/` directory. The commands check the known result and compare it with the host run. When using these commands in CI, use an empty output directory so an earlier file cannot mask a failed run. Add `/container-out/` to both ignore files. Try a missing input file and check that the container exits with an error.

== 4. Verify in CI and prepare a release

In your existing workflow, build the image after the C++ tests pass. Run the image with the sample input and check the output on the runner. This tests the final image as a user would run it.

For a delivery tag, publish the image to GitHub Container Registry (GHCR) after the checks pass. To automate the publication, use a job restricted to a push of a delivery tag. Give that job `contents: read` and `packages: write` and authenticate with the workflow's `GITHUB_TOKEN`. Verify that your instructor can pull the package. Keep the package private for a private assignment. See the https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry[GitHub Container Registry guide].

Keep run artifacts and release assets distinct. Attach PDFs to the workflow run for review and to the GitHub Release for a tagged delivery. Link the matching image tag or digest and give the exact command, input and expected output for one reproducible run. The xref:software:release-engineering-weather.adoc[release engineering lesson] shows the difference using a separate project.
