= C++ repository organization and CMake
:page-pagination:

A scientific program should make it easy to locate a calculation, test it and run it on new inputs. This page shows how to organize a small C++ program, compile it by hand and describe the same build with CMake.

The example reads two coordinates from a text file and writes their Euclidean norm to a second file. For the input `3 4`, the expected result is 5.

[#code-organization]
== Organize code by responsibility

Start with the path your data takes through the program. In the FEM project, `main()` reads the arguments and coordinates the work. A mesh reader turns a file into mesh data. The numerical code takes those data, assembles and solves the system, and returns the result. A writer saves the result for visualization.

*Keep computation separate from file handling.* A numerical function should take the data it needs and return its result. It can then be tested with a few values or a tiny mesh constructed in memory. Test mesh reading and result writing separately with small files.

*Keep dependencies easy to follow.* The executable can call the library, and the tests can call that same library. The calculation needs no knowledge of command-line arguments, output paths or the tests. When adding a feature, ask which component should own it and what information it needs from the others.

*Keep related files together.* In this example, `vector_norm.hpp` declares what callers can use and `vector_norm.cpp` defines what the function does. Keep them side by side in `src/`. Include the header where you call the function and in the file that implements it. Document assumptions about inputs and results at the interface.

A small project can start with one library target, one executable and one `CMakeLists.txt`:

[source,text]
----
project/
├── CMakeLists.txt
├── src/
│   ├── vector_norm.hpp  # Library interface
│   └── vector_norm.cpp  # Library implementation
├── app/
│   └── main.cpp         # Executable entry point
├── tests/              # Test programs and small fixtures
├── meshes/             # FEM input meshes
└── README.adoc          # Build, test and run instructions
----

[#separate-public-headers]
.Alternative layout for public headers
[NOTE]
====
A project can keep public headers under `include/<project>/` and implementation files under `src/`. This layout is useful when other projects install and use the library because it makes the public interface easy to find and package. Private headers can stay beside the code that uses them.
====

As the FEM project grows, group related files by responsibility. For example, put mesh reading in `src/mesh/` and assembly in `src/assembly/`, with each component’s headers and implementations together. Create a separate CMake target when you need to build or reuse that component independently.

[#build-stages]
.What do the preprocessor, compiler and linker do?
[%collapsible%open.proof]
====
The `c++` command coordinates several tools when you build a program.

Preprocessor::
Prepares one source file at a time. When it sees `#include "vector_norm.hpp"` in `main.cpp`, it inserts the header contents so the compiler can see the function declaration. It also handles directives such as `#define`. A missing header is reported at this stage.

Compiler::
Checks the prepared C++ code for issues such as a syntax error or a wrong argument type, then translates it into instructions. The assembler packages those instructions into an *object file* such as `main.o`. The option `-c` stops the build at this file.

Linker::
Connects references in object files to definitions in other object files or libraries. Here it connects the call in `main.o` to the implementation in `vector_norm.o` and produces the executable. If you omit `vector_norm.o` from the manual link command, you get an error such as `undefined reference` or `undefined symbol`.

After creating the files below, use `-E` to stop after preprocessing:

[source,bash]
----
c++ -std=c++17 -Isrc -E app/main.cpp
----

Look for the declaration `double vector_norm(double x, double y);` among the expanded includes.
====

[#build-outputs]
.Library or executable?
****
*Executable.* A program you can run, such as `vector-norm`. Its `main()` function is where your C++ code starts running.

*Library.* Reusable code that other programs or tests can call. In this example the library provides `vector_norm()`, and the executable handles the input and output files.

* *Static library* (`.a` on Linux). An archive of compiled code. When you link a program, the linker copies the parts it needs into the executable.
* *Shared (dynamic) library* (`.so` on Linux). The linker records a dependency. The library stays in a separate file and is loaded when the executable runs, so the file must be available at run time.

Compilation first turns each `.cpp` file into an *object file* (`.o`). It contains compiled code ready for the linker. CMake sets the appropriate compiler options when building a shared library. The diagram shows the two possible library builds. The example builds a static library.

image::repo/cpp-build-outputs.svg[Each C++ source compiles to an object file. The calculation object becomes a static or shared library. The application object and one of those libraries are linked into the executable.,640]
****

== Separate the calculation from file handling

In a practice directory, declare the function in `src/vector_norm.hpp`:

[source,cpp]
----
#pragma once

double vector_norm(double x, double y);
----

Put the implementation in `src/vector_norm.cpp`:

[source,cpp]
----
#include "vector_norm.hpp"
#include <cmath>

double vector_norm(double x, double y) {
    return std::hypot(x, y);
}
----

Put the executable entry point in `app/main.cpp`:

[source,cpp]
----
#include "vector_norm.hpp"
#include <cmath>
#include <fstream>
#include <iostream>
#include <string>

int main(int argc, char* argv[]) {
    if (argc != 3) {
        std::cerr << "Usage: vector-norm INPUT OUTPUT\n";
        return 2;
    }

    std::ifstream input(argv[1]);
    double x, y;
    std::string extra;
    if (!(input >> x >> y) || !std::isfinite(x) || !std::isfinite(y) || (input >> extra)) {
        std::cerr << "Expected two finite numbers in " << argv[1] << '\n';
        return 1;
    }

    std::ofstream output(argv[2]);
    output << vector_norm(x, y) << '\n';
    output.close();
    if (!output) {
        std::cerr << "Could not write " << argv[2] << '\n';
        return 1;
    }
}
----

`main()` handles arguments, file paths and errors. The library takes numbers and returns a number. This lets a test call the calculation directly.

== Compile and link once by hand

[source,bash]
----
mkdir -p build
c++ -std=c++17 -c src/vector_norm.cpp -o build/vector_norm.o
c++ -std=c++17 -Isrc -c app/main.cpp -o build/main.o
c++ build/main.o build/vector_norm.o -o build/vector-norm

mkdir -p samples out
printf '3 4\n' > samples/vector.txt
./build/vector-norm samples/vector.txt out/norm.txt
cat out/norm.txt
----

The first two compiler commands each produce an object file. The second uses `-Isrc` so `app/main.cpp` can find the library header. The last command links both objects into an executable. Try the link command without `build/vector_norm.o` and locate the missing symbol in the error message. Add `/build/` and `/out/` to `.gitignore` before committing.

== Build with CMake

[#what-is-cmake]
.What does CMake do?
[%collapsible%open.proof]
====
CMake is a widely used tool for configuring C++ builds. You describe what to build in `CMakeLists.txt`. A *target* is a named item in that description, such as the `vector_norm` library or the `vector-norm` executable. Each target records its source files and requirements, including dependencies and the C++ standard.

During *configuration*, CMake reads that description, detects the compiler and generates build rules for a tool such as Ninja. During the *build*, Ninja follows those rules and calls the compiler and linker. When you edit a source file, Ninja uses the dependencies to rebuild the affected files. The same `CMakeLists.txt` describes the build on your computer and in CI. See the https://cmake.org/cmake/help/v3.28/manual/cmake.1.html[CMake command reference].
====

[#first-cmake-build]
=== Build one executable

Create `CMakeLists.txt` at the root of your practice project. Start with one target containing both source files, as in the manual build.

[source,cmake]
----
cmake_minimum_required(VERSION 3.22)                         # <1>
project(VectorNorm LANGUAGES CXX)                            # <2>
add_executable(vector-norm app/main.cpp src/vector_norm.cpp) # <3>
target_include_directories(vector-norm PRIVATE src)          # <4>
target_compile_features(vector-norm PRIVATE cxx_std_17)      # <5>
----
<1> Require CMake 3.22 or later.
<2> Name the project `VectorNorm` and enable the C++ language (`CXX`).
<3> Compile the two sources and link their object files into the `vector-norm` executable.
<4> Add `src/` to the header search path for this target, just as `-Isrc` did in the manual command. `PRIVATE` applies the setting to this target.
<5> Require C++17 or newer when building the executable.

Configure, build and run from the directory containing `CMakeLists.txt`:

[source,bash]
----
cmake -S . -B build/basic -G Ninja
cmake --build build/basic
./build/basic/vector-norm samples/vector.txt out/norm.txt
cat out/norm.txt
----

Expected result: `5`, just as in the manual build.

[#cmake-command-options]
.Read the configure and build options
[%collapsible.proof]
====
[cols="1,3",options="header"]
|===
|Option |What it does here

|`-S .`
|Use the current directory (`.`) as the source tree. This is where CMake reads `CMakeLists.txt`.

|`-B build/basic`
|Put generated build rules, object files and binaries in `build/basic/`, outside the source directories.

|`-G Ninja`
|Generate rules for Ninja, the build tool installed above.

|`--build build/basic`
|Run the build tool with the rules that were generated in `build/basic/`.
|===
====

[#make-and-ninja]
.How do Make and Ninja build in parallel?
[%collapsible%open.proof]
====
Make and Ninja read the rules generated by CMake. The rules say what each job needs and which file it produces. Both tools skip steps whose outputs are up to date. They can start independent jobs at the same time and wait where one job needs the result of another.

[cols="1,2,2",options="header"]
|===
|Build tool |File generated by CMake |Parallel jobs

|Ninja
|`build.ninja` with `-G Ninja`
|Runs jobs in parallel by default. Use `-j2` to allow at most two jobs.

|GNU Make
|`Makefile` with `-G "Unix Makefiles"`
|Runs one job at a time by default. Use `-j2` to allow at most two jobs.
|===

In the two-source example, each compile job can start without waiting for the other. Linking can start only when both object files are ready.

image::repo/cmake-parallel-build.svg[CMake produces rules for Ninja or Make. Either tool can compile main.cpp and vector_norm.cpp in parallel. The linker waits for both object files before creating vector-norm.,600]

Try the same job limit through CMake with either generator. Use `--clean-first` to see both compile jobs again in the existing Ninja build. Generate the Make rules in a separate build directory.

[source,bash]
----
cmake --build build/basic --clean-first --parallel 2
cmake -S . -B build/make-basic -G "Unix Makefiles"
cmake --build build/make-basic --parallel 2
----

For an incremental build, run `ninja -C build/basic -j2` or `make -C build/make-basic -j2` from the project root. With `--target vector-norm` you can request that executable by name. Use `--target help` to see targets offered by your build. Later, CPack adds xref:m1:workflow.adoc#cpack-build-targets[targets for binary and source packages].
====

[#cmake-library-target]
=== Give the calculation its own target

The calculation will also be used in the tests. Keep the first two lines of `CMakeLists.txt` and replace the rest with a library target and an executable that links to it:

[source,cmake]
----
add_library(vector_norm STATIC src/vector_norm.cpp)          # <1>
target_include_directories(vector_norm PUBLIC src)           # <2>
target_compile_features(vector_norm PUBLIC cxx_std_17)       # <3>

add_executable(vector-norm app/main.cpp)                     # <4>
target_link_libraries(vector-norm PRIVATE vector_norm)       # <5>
----
<1> Build the static library. On Linux its file is `libvector_norm.a`.
<2> Make `src/` available to the library and to targets that use it. This is what `PUBLIC` means here.
<3> Require C++17 or newer for the library and propagate that requirement to its callers.
<4> Compile the application's entry point in the executable target.
<5> Make `vector_norm` a dependency of the executable. The executable uses the library's public settings and links the library's compiled code.

Use a different build directory for Debug. The added option `-DCMAKE_BUILD_TYPE=Debug` sets a CMake variable at configure time. With Ninja, this selects the Debug configuration, which includes information that helps a debugger match the executable to the source code.

[source,bash]
----
cmake -S . -B build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug
./build/debug/vector-norm samples/vector.txt out/norm.txt
cat out/norm.txt
----

Verify that the result is still `5`. In the testing section, a test program will link against the same `vector_norm` library.

.Observe what is rebuilt
[TIP]
====
After changing `src/vector_norm.cpp`, run `cmake --build build/debug --verbose`. Read the compiler command for the changed file and the command that relinks the executable.
====

[#cmake-eigen]
=== Declare Eigen as a dependency

Add these lines after the library target is defined:

[source,cmake]
----
find_package(Eigen3 REQUIRED CONFIG)                         # <1>
target_link_libraries(vector_norm PRIVATE Eigen3::Eigen)     # <2>
----
<1> Find the CMake configuration provided by the installed Eigen package (`CONFIG`). `REQUIRED` stops configuration if Eigen is missing.
<2> Attach the `Eigen3::Eigen` target to `vector_norm`. Eigen is a header library, so this gives the compiler the include paths it needs. The `PRIVATE` setting keeps Eigen out of the library's public interface.

Replace the implementation file's `<cmath>` include with `<Eigen/Core>` and change the function body to `return Eigen::Vector2d{x, y}.stableNorm();`. Configure, build and run again. The output for the sample remains `5`. Eigen is private to this target because the public header uses only built-in types.

See the https://libeigen.gitlab.io/eigen/docs-3.4/TopicCMakeGuide.html[Eigen CMake guide].

If configure cannot find Eigen, check that its development package is installed in the environment where CMake is running. Avoid hard-coding an include path from your laptop.
