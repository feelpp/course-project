= Deploy {feelpp} on Gaya with Slurm and Apptainer

== Objective

Operate on Gaya to run a {feelpp} heat simulation through Slurm, preserve its inputs/results and repeat it. This is the course's scientific deployment target and the starting point for the xref:mlops/project.adoc[simulation-to-ML pipeline]. The xref:containers:apptainer/tutorial.adoc[CSV exercise] is only a short runtime check before this application.

== Prepare an image and case

For the second two-hour M2 session, follow xref:session2-thermal-fin.adoc[the 3D thermal-fin practical]: the official Python generator, Heat runs at one and four ranks, and ParaView. The thermal bridge below remains another reference case.

Use xref:m1:gaya.adoc[Gaya access/storage guidance]. The instructor must validate the image, case and resource request on the course allocation before teaching. The explicit release below is the example documented by https://docs.feelpp.org/user/latest/install/containers.html[{feelpp}]; it is a reproducible starting version, not a claim that it is the newest or already validated on Gaya.

Prepare files once on the approved download/build host or shared project area, not inside every batch job. If students lack registry access, distribute the preflighted SIF with its checksum.

[source,bash]
----
mkdir -p feelpp-lab/case feelpp-lab/results
cd feelpp-lab
apptainer pull feelpp.sif oras://ghcr.io/feelpp/feelpp:v0.111.0-preview.10-noble-sif
apptainer inspect feelpp.sif
sha256sum feelpp.sif > feelpp.sif.sha256

case_revision=44487393868854b53e47e82217d3a0fbc557c8d1
case_url="https://raw.githubusercontent.com/feelpp/feelpp/$case_revision/toolboxes/heat/cases/Building/ThermalBridgesENISO10211"
for case_file in case2.cfg case2.json case2.geo; do
    curl --fail --location "$case_url/$case_file" --output "case/$case_file"
done
sha256sum case/case2.* > case.sha256
----

This stages a two-dimensional thermal-bridge case from the matching {feelpp} source revision. Keep all three files together: the CFG refers to the JSON, which refers to the geometry. Preserve the original baseline before varying inputs. See the https://docs.feelpp.org/user/latest/using/toolboxes/heat.html[heat toolbox interface] and https://github.com/feelpp/feelpp/tree/44487393868854b53e47e82217d3a0fbc557c8d1/toolboxes/heat/cases/Building/ThermalBridgesENISO10211[pinned case source].

== First batch run: one rank

Save `feelpp.sbatch` in `feelpp-lab`. Add the course partition/account and module setup if required. This is a single-rank baseline, before tackling host/container MPI compatibility.

[source,bash]
----
include::example$feelpp.sbatch[]
----

The command uses the toolbox executable directly with `exec`, explicit inputs and a writable result directory. The case configuration specifies dimension and discretization. Each job gets a separate result directory. All {feelpp} execution, including the version check, happens inside the allocation.

[source,bash]
----
sbatch feelpp.sbatch
squeue -u "$USER"
----

Note the returned job ID. Inspect `feelpp-JOBID.out`, `feelpp-JOBID.err` and `results/JOBID/`, replacing `JOBID`. Where available, check `sacct -j JOBID --format=JobID,State,ExitCode`. Locate measure CSVs and exported fields; do not equate a Slurm `COMPLETED` state with a scientifically valid solution. Record solver convergence and compare the original case's checks with its documented reference values.

== From one run to a dataset

Add a named spatial-average measure under `PostProcess.heat.Measures.Statistics` in a copy of the case JSON, alongside existing statistics:

[source,json]
----
"mean_temperature": {
    "type": "mean",
    "field": "temperature"
}
----

This represents the domain integral of temperature divided by domain measure, not the arithmetic mean of mesh-node values. The documented CSV column is `Statistics_mean_temperature_mean`; inspect the actual output header for the selected release during preflight. The https://docs.feelpp.org/toolboxes/latest/modeling-analysis-using-json-files.html[{feelpp} postprocessing reference] describes these statistics.

Run the unmodified baseline first. For parameterized cases, upstream reference checkers containing fixed expected values may no longer apply: preserve them for the baseline and replace them with checks justified for the changed parameters. Never silently ignore a checker failure.

== Exercise and verification

Repeat one case with the same SIF and inputs. Compare mean temperature, convergence and exported fields with an agreed tolerance. Then vary one boundary temperature in a copied case, predict the qualitative effect, and submit another job. After reviewing an intentional input change, regenerate that case's manifest (`sha256sum case/case2.* > case.sha256`) before submission; the batch script rejects input bytes that do not match it. Preserve the previous inputs and manifest with the previous run. Record the parameter values, units, input hashes, image hash, job ID and scalar output together.

Parallel execution is a later extension: use the site's supported MPI launcher and matching PMI/PMIx/MPI libraries. Do not merely increase `--ntasks`: incompatible launches can create independent one-rank simulations writing the same files. Validate rank count and one-versus-many-rank results first. See https://apptainer.org/docs/user/latest/mpi.html[Apptainer MPI guidance].

== Thermal-fin campaign with a Slurm job array

After validating the single 3D thermal-fin case, prepare all approved parameter samples, JSON files and meshes *before* submission. Give each sample a stable identifier. The following layout keeps the inputs and results on shared storage accessible from compute nodes:

[source,text]
----
campaign/
├── feelpp.sif
├── samples.txt                 # one sample ID per line, no header
├── cases/
│   ├── sample-0000/            # case.cfg, JSON, mesh and local dependencies
│   └── sample-0001/
├── logs/
├── runs/
└── slurm/heat-array.sbatch
----

The manifest order defines the mapping from zero-based task index to sample ID. For example, line 1 of `samples.txt` is task 0. Freeze the manifest for a submitted array; never reorder it while tasks are queued or running. Each CFG must resolve its JSON and mesh from its own case directory, without relying on paths from another sample. Keep a separate parameter/mesh manifest so every ID can be traced back to latexmath:[(L,t,\mathrm{Bi})].

Save this single-rank starting point as `slurm/heat-array.sbatch` in `campaign/`. Adjust the partition, account, modules, image path, resources and MPI launcher only after the corresponding single-case run has been validated on Gaya:

[source,bash]
----
#!/bin/bash
#SBATCH --job-name=thermal-fin
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=4G
#SBATCH --time=00:15:00
#SBATCH --output=logs/heat-%A_%a.out
#SBATCH --error=logs/heat-%A_%a.err
set -euo pipefail

campaign_root="$SLURM_SUBMIT_DIR"
task_id="$SLURM_ARRAY_TASK_ID"
sample_id="$(sed -n "$((task_id + 1))p" "$campaign_root/samples.txt")"
[[ "$sample_id" =~ ^[A-Za-z0-9_-]+$ ]] || {
    echo "Invalid or missing sample ID for task $task_id" >&2
    exit 1
}

case_dir="$campaign_root/cases/$sample_id"
[[ -f "$case_dir/case.cfg" && -f "$campaign_root/feelpp.sif" ]] || {
    echo "Missing CFG or SIF for $sample_id" >&2
    exit 1
}

run_dir="$campaign_root/runs/${SLURM_ARRAY_JOB_ID}_${task_id}"
mkdir "$run_dir"  # fail rather than overwrite an earlier attempt
mkdir "$run_dir/case" "$run_dir/results"
cp -R "$case_dir/." "$run_dir/case/"
printf 'sample_id=%s array_job=%s task=%s run_dir=%s\n' \
    "$sample_id" "$SLURM_ARRAY_JOB_ID" "$task_id" "$run_dir"

# Add the site-approved module setup here if required.
srun --mpi=none apptainer exec --cleanenv \
    --bind "$run_dir/case:/case:rw,$run_dir/results:/results:rw" \
    --env OMP_NUM_THREADS=1 \
    "$campaign_root/feelpp.sif" feelpp_toolbox_heat \
    --config-file /case/case.cfg --directory /results
----

From `campaign/`, first submit a small smoke subset, then the full approved set. Choose the concurrency limit with the teaching team; here two tasks may run simultaneously:

[source,bash]
----
mkdir -p logs runs
sample_count="$(awk 'END { print NR }' samples.txt)"
test "$sample_count" -gt 0
smoke_last=1
if [ "$sample_count" -eq 1 ]; then smoke_last=0; fi
sbatch --array="0-${smoke_last}%2" slurm/heat-array.sbatch
# After checking both results, submit the approved full campaign:
sbatch --array="0-$((sample_count - 1))%2" slurm/heat-array.sbatch
squeue -r -u "$USER"
sacct -j ARRAY_JOB_ID --format=JobID,State,ExitCode
----

The smoke command selects one task when the manifest has one entry and two otherwise. Wait for it and inspect its results before running the full-campaign command; these are separate submissions and have separate job IDs. Slurm reports the array job ID at submission; task `k` appears as `ARRAY_JOB_ID_k` and writes `logs/heat-ARRAY_JOB_ID_k.*`. Each task copies its case into a private writable directory because mesh import may create partitioning files. The result directory is isolated by array job ID and task index; a retry should use a new submission and retain the previous logs and outputs.

After all tasks finish, match each task index to its frozen sample ID and validate its exit status, solver convergence, mesh and marker checks, and `mean_root_temperature` CSV value before admitting it to the learning dataset. Failed tasks should be recorded and resubmitted selectively, for example `sbatch --array=3,7%2 slurm/heat-array.sbatch`; the original manifest indices still identify the samples. An array runs independent simulations; it does not make one simulation an MPI computation. See the xref:m1:gaya.adoc[Slurm overview], https://slurm.schedmd.com/job_array.html[official job-array guide] and xref:mlops/project.adoc[project workflow].
