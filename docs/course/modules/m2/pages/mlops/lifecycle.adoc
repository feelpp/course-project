= Simulation data, training and experiment records

== Define the scientific contract

The input is the vector `(L, t, Bi)`; the target is the mean temperature on the designated fin-base surface, extracted from a verified 3D {feelpp} heat simulation. Use a central post with four fins. Keep the remaining generator/model settings, including the prescribed maximum heat flux, fixed and documented.

The teaching team supplies the bounds and units for `L`, `t` and `Bi`, the exact heat-flux value, mesh policy, sample budget and numerical acceptance tolerance. Do not reuse the thermal-bridge example domain for this project. Agree these values before generating a campaign.

The CPU heats the lower face of the central post. Heat is conducted through the post and fins and leaves through the surfaces exposed to ambient air. The simulation solves conduction only; the ambient exchange is represented by the nondimensional Robin condition controlled by `Bi`. Define the target as the surface integral divided by the area of the heated CPU/post interface marker. Record the generator's nondimensional convention, marker and units. Do not use an unweighted average of mesh-node values as an undocumented substitute.

Use the notation `mu=(L,t,Bi)` for one point in the admissible parameter space `P` and define the associated scalar functional by `S(mu)=Tbar_base(mu)`, the mean temperature on the heated CPU/post base. The surrogate model learns the mapping `mu -> S(mu)`. The temperature field is a richer solver output, whereas `S` is the typical quantity of interest passed to the dataset and the learning algorithm.

== Prepare inputs and execute the campaign

. Generate a small seeded smoke design in the approved three-dimensional `(L, t, Bi)` domain; expand only after validation and a resource estimate.
. Assign a stable `sample_id` to each parameter vector and materialize its complete CFG/JSON/geometry inputs in a separate directory. Use a parser supporting the upstream JSON comments or an instructor-normalized JSON template.
. Modify the actual `L`, `t` and `Bi` inputs in the generator/model. Record resolved values and checksums; test that modifying each parameter changes the corresponding solver input and, where applicable, regenerates the 3D mesh.
. Submit jobs on Gaya using the xref:feelpp-gaya.adoc[validated Slurm/Apptainer procedure]. For arrays, map each array index to one manifest row and limit concurrency to the agreed allocation.
. Record sample/job IDs, image hash, code/template revision, inputs, exit status, convergence and output location. Classify missing, failed and successful runs explicitly. Retry with a recorded attempt ID; do not silently alter the sampling distribution.

Each attempt needs an isolated output directory. Job submission is asynchronous: collect only after completion checks. A scheduler dependency such as `afterok` can order stages, but scientific checks must still validate the outputs.

== Assemble and freeze the dataset

Extract the named mean-base-temperature statistic from the measure CSV. Require the expected base marker/column, finite scalar value, matching sample identity and successful numerical checks. For transient models define which time/steady-state criterion is used; do not silently select the last row.

A minimal table contains `sample_id`, `L`, `t`, `Bi` with declared units, `mean_base_temperature`, case/mesh hash, simulation SIF hash and output identity. Keep detailed job/attempt records in a related manifest. Reject duplicate samples, missing outputs and non-finite values; report failed samples instead of filling them with zero.

Freeze a dataset version/checksum and explicit lists of train, validation and test sample IDs. Replicates or variants of the same parameter point must remain in the same group. Fit preprocessing only on training data. Use validation or grouped cross-validation for choices, and open the held-out test results once for final assessment. A smoke campaign checks plumbing; it is too small for strong accuracy claims. One-rank and four-rank reruns of the same parameter point are numerical verification, not independent samples.

== Train and compare

Start with `DummyRegressor` as a mean-prediction baseline and a small scaled regression pipeline, such as `StandardScaler` plus `Ridge`; a nonlinear regressor is an optional justified comparison. Keep configuration in Git: feature names/order, seed, split manifest, model parameters and output directory.

Report MAE and RMSE in temperature units, maximum absolute error and residuals against the physical parameters. Compare the surrogate error with simulation discretization error. Use https://scikit-learn.org/stable/common_pitfalls.html[scikit-learn's leakage and randomness guidance].

== Track experiments and artifacts

Use a local MLflow store with one record per training configuration. Around the implemented training/evaluation function:

[source,python]
----
import mlflow

mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment("feelpp-mean-temperature")
with mlflow.start_run():
    mlflow.log_params(config)
    mlflow.set_tags({"git_commit": commit_sha, "dataset_sha256": dataset_sha256})
    metrics, model_path = train_and_evaluate(config)
    mlflow.log_metrics(metrics)
    mlflow.log_artifact(str(model_path), artifact_path="model")
    mlflow.log_artifact("run-manifest.json")
----

This is an integration fragment: students implement `train_and_evaluate`, resolve the scalar `config` and write the manifest first. Include the simulation SIF, ML environment, split IDs, feature schema and target definition in the manifest. Record validation metrics during model choice and label final test metrics distinctly.

Persist the fitted preprocessing/model pipeline, schema, valid parameter domain, environment versions and run identity. Keep the MLflow database and artifact storage together when handing off runs; a database alone does not contain the models. Use only trusted serialized Python models with verified integrity. See https://mlflow.org/docs/latest/ml/tracking/quickstart/[MLflow tracking].
