*M2 · 14 September 2026 · 2 hours · Mini-project in pairs.*

Build and verify a heat-transfer simulation using an existing Python generator. You will produce the inputs, run the {feelpp} Heat toolbox in Apptainer on Gaya, and compare runs with one and four MPI ranks before visualizing the results in ParaView.

This session builds on the xref:containers:apptainer/tutorial.adoc[Apptainer practical] and prepares you for the xref:mlops/project.adoc[simulation → data → training → inference → verification pipeline]. You are responsible for creating the case files and Slurm script; the guidance below provides starting points and success criteria.

== Objective of the mini-project

The goal is to develop the complete solution as a reproducible workflow, in a pair. The workflow starts from a parameter space and a sampling budget, generates one 3D case and mesh for each sampled point, launches the simulations, collects the quantity of interest, trains the team's selected model, and verifies its predictions against finite-element results.

The workflow may run locally, on Gaya, or across both environments. What matters is that every transition is automated and documented: inputs → sampling → case and mesh generation → Slurm/Apptainer execution → collection on Gaya → dataset → training → inference → verification. A manual operation is acceptable for an exploratory check, but it must not be required for the reproducible campaign.

== Physical interpretation

The case represents a CPU heating the lower face of a central post. The heat is conducted through the post and the four horizontal fins, then transferred to the ambient air from the exposed surfaces. Only the solid Heat problem is solved; the air flow is not meshed or solved.

The generator uses nondimensional variables. The CPU boundary carries the prescribed heat flux, while the ambient exchange is represented by a convective (Robin) condition whose nondimensional coefficient is the Biot number `Bi`. Use the generator's definitions and signs when interpreting the results, and document the reference scales before giving any dimensional interpretation.

== Geometry, mesh and temperature field

The following two views illustrate the expected outputs of the numerical stage. They are complementary: the mesh shows the discrete finite-element problem, while the temperature field shows the computed physical response.

image::thermal-fin-mesh-3d.png[3D tetrahedral mesh of the four-fin heat sink,align="center",width=900]

.*Figure 1. 3D mesh.* The volume is discretized with tetrahedral elements around the central post and the four fins. Before launching a campaign, check the element quality, the four-fin geometry, the `Gamma_root` marker and all external markers. A successful meshing command alone is not evidence that the physical groups required by the Heat model are correct.

image::thermal-fin-temperature-3d.png[3D temperature field in the four-fin heat sink,align="center",width=900]

.*Figure 2. 3D temperature visualization.* The warmest region is expected near the heated CPU/root and the post; temperature decreases along the fins as heat is transferred to the ambient. The colour scale and the nondimensional convention must be recorded. This view is for physical interpretation and debugging; the scalar used by the MLOps model must come from the documented average on `Gamma_root`.

For each sampled parameter vector, the workflow should preserve both the generated mesh and the visualization-ready result. The mesh is an input to the solver; the temperature field is an output used for inspection and, together with the root statistic, for verification.

== From simulations to a learned mapping

Denote a parameter point by latexmath:[\mu=(L,t,\mathrm{Bi})]. The solver associates with it the functional

[latexmath]
++++
S(\mu)=\overline{T}_{\mathrm{root}}(\mu),
++++

the mean temperature on the heated CPU/post root. Learning does not replace the finite-element solver during data generation: it learns the mapping latexmath:[\mu \mapsto S(\mu)] from the verified simulation database. This scalar latexmath:[S] is the typical quantity of interest used for training, prediction and error assessment; the complete 3D temperature field is retained for visualization and scientific checks.

As a final application, the validated surrogate can support rapid optimization. For a design study, search over latexmath:[(L,t,\mathrm{Bi})] for the admissible configuration with the lowest base temperature (or another explicitly stated objective). For an operational study, fix the geometry and optimize the permitted operating parameter(s) to meet a target or limit. The selected candidate must always be confirmed by a new finite-element run.

== Prepare a consistent Heat problem

We solve steady-state conduction in the solid. A boundary condition describing heat exchange with the surroundings does not imply that we solve the airflow: we use only the Heat toolbox.

Starting from the generated model:

. Identify the conductivities, the `Bi` parameter and the external temperature; distinguish the values used by Heat from the bounds intended for a parameter study.
. Identify the conditions at the base and on the external surfaces. Is a temperature or a flux prescribed at the base?
. Explain the meaning of the case's normalized values. Do not report degrees Celsius or millimetres without defining a consistent physical scaling.
. Prepare a configuration for Heat. Separate solver options from those related to model order reduction; preserve the upstream files so you can explain your changes.
. Set up the mean root-temperature measure described in <<measure-and-compare,Measure and compare>> so it is available in both runs.
. Choose a mesh size suitable for a quick trial and generate a 3D mesh with Gmsh. The value `h=0.2` is a starting point for this small case; it does not replace a convergence study.

*Hints:* read `gmsh -help` for the dimension, format and output-file options; use MSH 2 format for this practical. Gmsh must support OpenCASCADE, either in the image or in the provided native installation. Examine the messages and mesh quality, not just the exit code.

In Gmsh, check the volumes, physical groups and actual location of the base surface. A name appearing in the JSON does not prove that the correct set of elements is selected.

Next, configure the mesh import in the Heat JSON. Use *the same mesh file* to compare one and four ranks. The `Meshes.heat.Import` section and its partitioning option are described in the https://docs.feelpp.org/toolboxes/latest/modeling-analysis-using-json-files.html[JSON model documentation]. The `$cfgdir` symbol lets you reference a file relative to the CFG directory.

*Checkpoint:* another pair must be able to follow the CFG → JSON → mesh chain and verify that the required markers exist. Note that the upstream JSON contains `//` comments, which strict JSON validators do not accept.

== Run Heat on Gaya

=== Build a first job using one rank

Write your Slurm script using what you learned in the previous session. It must:

* Request modest resources for a one-rank run and preserve standard output and error logs.
* Launch `feelpp_toolbox_heat` inside the image using `apptainer exec`.
* Pass the CFG with `--config-file` and explicitly select the results directory with `--directory`.
* Make the inputs accessible inside the container and keep the outputs on Gaya after execution.
* Isolate each job's results and record the environment and inputs used.

Consult the https://docs.feelpp.org/user/latest/using/toolboxes/heat.html[Heat toolbox interface] and the first-session material if you get stuck. Consider paths as seen from the host and from the container. If importing the mesh creates partitioning files, provide a writable working copy of the inputs for each job.

Submit with `sbatch`, monitor with `squeue`, then examine the logs and, where available, `sacct`. Locate the result files without assuming they were written to the current directory.

*Checkpoint:* demonstrate solver convergence and a usable temperature field. A Slurm `COMPLETED` state alone does not validate the solution.

=== Adapt your launch to four ranks

Keep exactly the same problem, mesh and numerical settings. Adapt the Slurm request and launch to use four ranks on a single node.

Use the launcher validated by the instructor: the hybrid model starts processes with Gaya's MPI, then runs {feelpp} inside Apptainer. The host and image MPI libraries must be compatible; see https://apptainer.org/docs/user/latest/mpi.html[Apptainer and MPI]. For a direct `srun` launch, use the PMI/PMIx plugin validated for this combination.

*Explain:* why is increasing `--ntasks` alone insufficient? Why are four independent processes different from a four-rank MPI computation? What would happen if `--cleanenv` removed the MPI environment?

Do not use `--mpi=none` for the multirank computation. Check the communicator size in the {feelpp} output; the exported `pid` field also helps inspect the partitions. Do not confuse this check with the number of tasks requested from Slurm.

=== Native alternative

If the instructor provides access to the native {feelpp} installation on Gaya, adapt your script to invoke the Heat toolbox directly with the specified {feelpp}/MPI modules. Keep the same CFG, JSON and mesh, and continue to isolate job results.

Record the version and modules: the native installation and SIF are separate environments. This alternative also allows you to continue the parallel work if the image's MPI has not yet been validated; state clearly which execution method you actually used.

[[measure-and-compare]]
== Measure and compare

Add the `mean_root_temperature` surface-average measure on `Gamma_root` to the generated model using `PostProcess.heat.Measures.Statistics`, as shown in the xref:mlops/project.adoc[project specification] and the https://docs.feelpp.org/toolboxes/latest/modeling-analysis-using-json-files.html#_statistics[{feelpp} JSON documentation]. Locate its column in the generated CSV before launching the campaign.

The quantity of interest is the mean temperature on the root surface, latexmath:[\overline{T}_{\mathrm{root}}=\frac{1}{|\Gamma_{\mathrm{root}}|}\int_{\Gamma_{\mathrm{root}}} T\,\mathrm{d}\Gamma]. State the nondimensional convention. Why is the arithmetic mean of the nodal values not necessarily equivalent to this surface average?

Compare one and four ranks in a small table of your own design: job IDs, environment, mesh hash, rank count, convergence, mean temperature and timings. Define a relative difference and propose a justified tolerance to discuss with the instructor. If the results differ, examine the inputs, convergence and MPI launch before attributing the difference to a physical effect.

Distinguish queue time, startup, partitioning, solving and writing. A very small case may be slower with four ranks; explain this result if it occurs.

*Hints:* locate the exported entry file (`.case` for EnSight, or `.pvd` if VTK is configured). Create a visualization that lets you:

. View the mesh and temperature with a readable legend.
. Examine the interior using a slice through the post and fins.
. Identify the heated base and interpret the observed gradients.
. Visualize the partitions using the parallel run's `pid` field.
. Compare one and four ranks using the same slice and colour scale.

Save an annotated screenshot and a ParaView state. Explain which files are still needed to reopen this state elsewhere. As an extension, investigate how to verify a volume average with the *Integrate Variables* filter.

== Prepare the MLOps parameter study

Once the reference case has been verified, prepare the full campaign over exactly three parameters: fin length `L`, fin thickness `t` and `Bi`. Keep the number of fins equal to four and use the largest heat flux prescribed for the campaign. Other generator/model parameters, including the fixed post setting, must be recorded and held constant.

Use a documented seeded sampling strategy over the approved three-dimensional domain. Predict the qualitative effect of each parameter and decide when a new 3D mesh is required. Create each case in a separate directory, preserve parameters and mesh checksums, then submit the campaign through a Slurm job array. Start with a smoke subset before the full design.

Propose a data-row schema linking `(L, t, Bi)` to `mean_root_temperature` and its provenance. Split the completed samples into disjoint train, validation and test sets before training. One-rank and four-rank runs of the same case are numerical verification runs, not two independent physical examples to split between training and testing.
